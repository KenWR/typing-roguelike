# Codex 활용 사례 로그

이 문서는 OpenAI 게임 해커톤 제출·발표에서 재사용할 수 있도록, 프로젝트 개발 과정에서 Codex가 어떤 문제를 다뤘고 사람의 결정과 어떻게 협업했는지 사례 단위로 기록한다.

## 기록 원칙

각 사례는 다음을 구분한다.

- **문제**: 팀이 해결해야 했던 실제 개발 문제
- **사람의 결정**: 제품 방향, 게임 규칙, 우선순위처럼 팀이 책임지고 결정한 내용
- **Codex 기여**: 저장소 탐색, 구현, 테스트, 리팩터링, 문서화 등 Codex가 수행한 작업
- **결과**: 코드·테스트·문서 등 검증 가능한 산출물
- **근거**: 관련 PR, 이슈, 파일 링크

새 사례는 추상적인 "AI로 개발했다"는 설명보다, 입력된 문제와 검증 가능한 결과를 연결해서 추가한다.

## 사례 1 — 전투 시스템을 독립 모듈로 분해

### 문제

타이핑 입력, AP, 공격 준비 시간, 방어 타이밍, 승패 처리가 한 흐름에 섞이면 게임 규칙을 수정하거나 테스트하기 어려워진다. 특히 해커톤 기간에는 기능을 빠르게 추가하면서도 기존 전투 규칙의 회귀를 막을 수 있어야 했다.

### 사람의 결정

- 전투의 핵심 재미를 `타이핑 입력 → 행동 선택 → AP/타이밍 계산 → 피해/방어 → 결과 처리` 흐름으로 유지한다.
- UI와 규칙 계산을 가능한 한 분리한다.
- 전투 규칙은 작은 모듈과 테스트 가능한 상태 전이로 구현한다.

### Codex 기여

저장소의 전투 영역을 기능 단위로 나누어 구현·정리하는 작업에 활용했다. 현재 전투 코드는 AP 자원, 콤보, 피해 계산, 방어 윈도우, 적 행동 선택, 승리/패배 및 결과 라우팅이 별도 모듈로 구성되어 있다.

### 결과

- `apps/game/src/game/combat/action-point-resource.ts`
- `apps/game/src/game/combat/combo-tracker.ts`
- `apps/game/src/game/combat/damage-formula.ts`
- `apps/game/src/game/combat/defense-window.ts`
- `apps/game/src/game/combat/enemy-attack-selection-loop.ts`
- `apps/game/src/game/combat/combat-victory.ts`
- `apps/game/src/game/combat/combat-defeat.ts`
- `apps/game/src/game/combat/combat-outcome-routing.ts`

이 구조 덕분에 UI 전체를 실행하지 않고도 핵심 전투 규칙을 개별적으로 검증할 수 있는 기반이 생겼다.

## 사례 2 — 데이터 기반 적·인카운터 초기화

### 문제

맵 노드에서 전투에 진입할 때 적 종류와 수, HP, 행동, 플레이어 장비/스킬을 일관된 방식으로 구성해야 한다. 화면 코드에서 직접 적 데이터를 조립하면 콘텐츠 추가와 밸런스 변경이 어려워진다.

### 사람의 결정

- 적과 인카운터 정의를 공유 콘텐츠 데이터로 관리한다.
- 맵 노드와 런 상태를 입력으로 받아 전투 초기 상태를 생성한다.
- 잘못된 노드나 누락된 콘텐츠는 전투 화면에서 임의 복구하지 않고 명시적인 실패 결과로 처리한다.

### Codex 기여

공유 설정(`ENCOUNTER_CONFIGS`, `ENEMY_CONFIGS`, `EQUIPMENT_CONFIGS`)과 런 상태를 연결하는 초기화 로직을 구현·정리하는 데 활용했다. 노드 타입 검증, 결정적 인카운터 선택, 장착 장비의 스킬 수집, 적 인스턴스 생성, 보상 정책 결정을 하나의 경계 함수로 모았다.

### 결과

- `apps/game/src/game/combat/encounter-initializer.ts`
- `packages/shared/src/content/enemies.ts`
- `packages/shared/src/content/encounters.ts`
- `packages/shared/src/content/types.ts`

전투 진입부가 콘텐츠 데이터와 런 상태 사이의 명확한 계약 역할을 하므로, 이후 적·엘리트·보스 콘텐츠를 추가할 때 화면 로직을 반복 수정할 필요가 줄어든다.

## 사례 3 — 프론트엔드와 백엔드 사이의 RunState 계약 정리

### 문제

MVP 우선순위는 브라우저에서 플레이 가능한 게임 루프를 먼저 완성하는 것이지만, 이후 런 저장·복구와 리더보드 같은 서버 기능을 붙일 계획이 있다. 프론트엔드 상태가 서버 저장 형식과 무관하게 커지면 통합 시점에 큰 재작업이 발생할 수 있다.

### 사람의 결정

- 현재는 프론트엔드 코어 게임플레이를 우선한다.
- 런 상태는 공유 타입을 기준으로 직렬화 가능한 데이터 계약을 유지한다.
- 백엔드 연결은 코어 루프를 막지 않도록 경계 모듈에서 처리한다.

### Codex 기여

런 상태와 API 지속성 경계를 문서·코드 수준에서 분리하고, 저장/복구 시 어떤 상태가 오가는지 추적 가능한 구조를 만드는 데 활용했다.

### 결과

- `docs/run-api-persistence.md`
- `apps/game/src/game/api/`
- `apps/game/src/game/run/`
- `packages/shared/src/`

이 구조는 해커톤 MVP에서는 로컬 게임 루프에 집중하면서도, 이후 서버 저장 기능을 연결할 수 있는 확장 지점을 남긴다.

## 사례 4 — 작업을 검증 가능한 GitHub 이슈 계약으로 변환

### 문제

해커톤 작업은 게임플레이, 에셋, 디자인 결정, 배포, 제출 문서가 동시에 진행된다. 단순 TODO 목록만으로는 완료 조건과 검증 방법이 모호해져 병렬 작업에서 충돌이 생기기 쉽다.

### 사람의 결정

- 프론트엔드 코어 게임플레이를 가장 먼저 완성한다.
- 각 작업은 우선순위와 단계, 유형을 구분한다.
- 구현 티켓에는 완료 조건뿐 아니라 테스트·타입체크·사용자 흐름 검증을 포함한다.

### Codex 기여

기획 내용을 구현 가능한 작업 단위로 분해하고, GitHub 이슈에서 작업 계약·완료 조건·검증·의존성을 읽을 수 있도록 구조화하는 데 활용했다. 이 문서가 연결된 #173 역시 동일한 형식의 작업 계약을 사용한다.

### 결과

- GitHub Issues 기반 작업 백로그
- 구현 이슈의 명시적 완료 조건과 검증 항목
- 프론트엔드 코어와 후속 작업을 구분한 단계별 실행 구조

## 발표·제출용 요약

Codex는 이 프로젝트에서 게임의 제품 방향을 대신 결정하는 역할이 아니라, 팀이 정한 규칙을 저장소 구조와 실행 가능한 코드로 빠르게 변환하고 검증하는 개발 파트너로 사용했다. 사람은 핵심 게임 루프, 우선순위, 밸런스와 UX 결정을 맡았고, Codex는 저장소 탐색, 모듈 분해, 구현, 테스트 가능한 경계 설계, 문서화와 작업 구조화에 기여했다.

특히 전투 시스템처럼 상태와 타이밍이 복잡한 영역을 작은 모듈로 분리하고, 적·인카운터를 데이터 기반으로 연결하며, 프론트엔드 우선 개발과 향후 서버 지속성 사이에 명확한 계약을 둔 것이 대표적인 활용 사례다.
